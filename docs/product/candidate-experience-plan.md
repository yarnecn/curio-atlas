# 候选与随手记体验方案

## 原则

记录时不要求用户成为编辑；公开前确保内容可读、可核验。统一的是公开内容约定，不是把所有入口变成同一张长表单。

## 第一阶段：阅读与投稿闭环（本次）

- 随手记及记录 API 保持私密、无标题也可保存，不进入公开列表或评分。
- 转投稿保留原文，用户确认标题（2～80 字）、摘要（12～160 字）、用途（12～300 字）及可选来源；不自动截断长内容。
- Web 与小程序候选有标题和详情入口，保留“试读、未正式收录”提示。
- 详情直接评分，失败不隐藏正文；未登录提供登录入口，作者提前看到不能自评的说明。首页试读卡同步提示作者身份。
- Web 登录后回到当前候选；小程序登录返回详情时重新读取身份。
- 评分仍以服务端校验为准，不改变初审、试读、正式审核规则。

验收：匿名可读；非作者可评分；作者不可自评；失败可重试且正文仍在；标题可搜索；用途长度与服务端一致。

## 第二阶段：草稿恢复与历史维护（待实现）

1. 结构化私密草稿保存完整投稿字段，返回明确的 draft 状态与草稿编号；只有作者可读写，重复请求幂等。
2. 转投稿失败保留草稿；成功建立候选关联，避免重复提交。两端均明确区分“保存私密草稿”和“提交审核”。
3. 旧客户端不带标题时采用版本化兼容协议；先部署支持草稿返回的客户端，再开启服务端降级保存。不能给旧客户端返回虚假的投稿成功。
4. 历史无标题候选提供管理员独立修改标题入口，记录审计且不改变状态、评分、作者或正文。正式收录前仍需确认。

当前限制：旧客户端缺标题仍会收到校验错误，尚未自动转存草稿；历史候选用话题占位标题，初审/正式审核可确认标题，但没有独立标题维护接口。

## 第三阶段：验证产品效果

观察随手记到投稿转化、候选详情点击率、有效评分参与率及校验失败率。优先解决用户流失点，不用新增必填项换取表面完整度；不以票数替代事实审核。
